# Sasta Milaga · Invoice QR and reference verification

Implemented: 2026-11-22.

## Available customer workflow

1. Customer submits the static checkout request at \`/order/\`. The form must receive a successful response from its configured Formspree receiver (or there is a previously acknowledged payment-pending request).
2. A **Generate invoice/reference QR** option becomes visible under the order status. The feature uses a locally vendored MIT-licensed QRCode.js library.
3. QR encodes **only** a verification page URL with the opaque request reference, e.g. \`https://sastamilaga.com/invoice/verify/?ref=SM-REQ-0123456789ABCDEF0123\`. Customer name, address, contact number, product contents, and payment tokens are NEVER encoded in the QR.
4. The verification page checks the reference **format only**. It explicitly displays **NOT VERIFIED**, because Formspree acknowledgement and PayPal redirect are not proof of accepted, paid, fulfilled, or invoiced orders.
5. Staff must cross-check the original intake entry, payment provider transaction ID/status and inventory/dispatch before issuing a real invoice. **Do not treat the QR, a screenshot, or a redirect as receipt of payment.**

## Distinction: generated QR vs. authenticated financial invoice

| Feature | Available | Authoritative? |
|---|---|---|
| Copy/scan random order request reference | Yes | No |
| Invoice-reference QR display after acknowledged request | Yes | No |
| Verifier rejects invalid reference format | Yes | Format check only |
| Payment-provider capture/refund verification | Not integrated | Requires secure server |
| Staff-issued tax invoice with number and legal tax details | Not integrated | Requires verified commerce system |
| Cryptographic signature on paid invoice | Not integrated | Requires merchant-held signing secret |
| Real-time WooCommerce/PayPal reconciliation | Not integrated | Requires authenticated webhook/API |

A **payment-verified invoice** must be generated by a trusted backend after the actual gateway capture is verified. Build a private, authenticated order/invoice ledger and webhook with signature and idempotency checks. Store the amount/currency, tax, order/payment IDs and authoritative status server-side. A QR should contain a random token or short URL, *not* personally identifiable information, card details or a self-declared \`paid=true\` flag. The public QR verification endpoint can then look up the server record and show a redacted, validated invoice state. Protect against enumeration and misuse using strong random tokens, throttling and expiration/rotation where appropriate.

## Audit and regression checks

- \`assets/js/order-reference-qr.js\` is the customer-side generator (no checkout capture).
- \`assets/vendor/qrcode-1.0.0.min.js\` and \`assets/vendor/qrcode-LICENSE.txt\` are the local licensed QR implementation.
- \`invoice/verify/index.html\` is the fail-closed, noindex, no-referrer verification page.
- \`tools/order-reference-qr.test.mjs\` tests that failed requests produce no QR and acknowledged requests generate only an opaque reference URL.
- GitHub Pages workflow runs this test during \`node --test\`; checkout and payment links are unchanged.

No order, payment or tax-invoice record is created by this feature; no WooCommerce payment or PayPal configuration is altered. Do not market the QR as a "verified paid invoice" until a signed backend integration is complete.
